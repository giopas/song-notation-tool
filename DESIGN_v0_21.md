# Song Notation Tool — design notes past v0.21

**What this is.** v0.21 shipped the lick changes (tab-shaped, blue,
empty-grid button, rests in grey). This document specifies the rest of
the list that came with them — the items that are genuinely new surface
rather than a fix to something already there. Read
[DESIGN_v0_16.md](DESIGN_v0_16.md) for the model and
[DESIGN_v0_17.md](DESIGN_v0_17.md) for the editor before implementing
any of it.

The ordering below is by *value per unit of risk*, not by the order the
items were written down. §1 and §2 are small and self-contained. §3 is
medium. §4 changes the data model. §5 is the one that should not be
built until it has been drawn on paper first.

---

## 1. Round-trip import — reopen a song from its own export

**The ask.** "Import from existing PDF, `.sng` or TXT from generated
songs (so to modify)."

Three formats, and they are three genuinely different problems. `.sng`
is the native save format, so importing one is a file-picker away from
free. TXT and PDF are *printed output*, and importing those is the part
that needs designing.

### 1.0 `.sng` — mostly already there

A `.sng` is the document, on disk, as JSON. `model.migrate()` already
brings an older one forward, so a file from any past version opens
correctly today. The desktop app already has this twice over — "📂 Open"
in the topbar and "📂 Import project" on the Start-here panel, both
`askopenfilename` onto `.sng`.

**The gap is the browser front end.** It can only open songs that are
already sitting in the songs folder (`GET /api/songs` lists that
directory); there is no way to bring in a `.sng` from a download, a USB
stick, or another machine. That is a small, standalone job and should be
done before anything in this section:

- an **Import…** button beside "New song" on the Start-here panel,
  opening a hidden `<input type="file" accept=".sng,.json">`,
- read it with `FileReader`, `JSON.parse`, and `POST /api/songs` — which
  already validates and migrates on the way in, so the front end does no
  checking of its own beyond "is this JSON at all",
- name-collision handling: the store already refuses to clobber, so on a
  clash offer the "(2)" suffix rather than failing,
- drag-and-drop onto the song list for free, since it's the same handler.

Maybe forty lines of `app.js` and one hidden input in `index.html`. No
server change at all.

**The trap** (this applies to TXT and PDF, not to `.sng`). The obvious
reading is *parse the printed page back into a
document*. Don't build that. The export is lossy by design: it resolves
references (`=Chorus_1` prints as the notes it points at), it drops riff
identity, it collapses `repeat` into `(x4)`, it wraps measures to fit a
page width, and it prints nothing at all about `render` mode or
per-section transpose. A parser would recover a plausible song, not *the*
song, and would silently degrade every file it touched. Worse, it would
have to be maintained in lockstep with every future change to the layout
— the layout being the thing most likely to change.

**The proposal.** Make the export carry the document with it. The
printed page stays exactly as it is; the file gains a machine-readable
payload that the importer reads and the human never sees.

### 1.1 TXT

Append a footer block after the existing generated-by banner:

```
================================================================================
  Generated by Song Notation Tool v0.21.0
  https://github.com/giopas/song-notation-tool
================================================================================

# song-notation-tool:document v1
# eJyrVkrLz1eyUsooKSkottLXLy8v1ytJLS7RS87PLc0rKSpNLdZLzs8tzSspKk0t...
# song-notation-tool:end
```

The payload is `base64(zlib(json.dumps(doc)))`, wrapped at 76 columns,
every line prefixed `# `. Properties worth keeping:

- It is inert. A `#`-prefixed tail can't disturb a chart anyone reads.
- It survives copy-paste through mail and chat, which a binary sidecar
  does not.
- It is *optional on read*: a TXT with no payload still imports through
  whatever best-effort parse exists later, or is refused cleanly.
- It should be suppressible — `--no-payload` on the CLI, a checkbox in
  the export dialog — for a chart being handed to another player, where
  a wall of base64 at the bottom is noise.

Size check: a twelve-section song is about 6–12 kB of JSON, so roughly
1.5–3 kB compressed and base64'd — 20 to 40 wrapped lines. Acceptable.
If it ever isn't, drop `lyrics_text` from the payload before compressing
and note the omission in the header line.

### 1.2 PDF

Same payload, but as a proper attachment rather than visible text. The
exporter already hand-writes the PDF object graph in `_assemble_pdf()`,
so this is a contained addition:

- one embedded file stream (`/Type /EmbeddedFile`, `/Filter
  /FlateDecode`) holding the raw JSON bytes,
- a `/Filespec` naming it `song.json`,
- an `/EmbeddedFiles` name tree on the catalog, plus `/Names`.

Roughly 40 lines in `_assemble_pdf()` and a new
`export.extract_payload(pdf_bytes)` that walks back out. Also set
`/Producer (Song Notation Tool <version>)` in the Info dictionary while
in there — a cheap way for the importer to reject a PDF that was never
ours before it goes looking for an attachment that isn't there.

A PDF printed from the *browser's* print dialog will not carry the
attachment. That's fine and should be stated in the help text: the file
saved from the app round-trips, a re-print of it does not.

### 1.3 The import path itself

One entry point, format-sniffed, so the three formats are one menu item
rather than three:

```python
# export.py
def extract_payload(data: bytes) -> dict | None:
    """The document a generated TXT or PDF carries, or None."""
```

and in both front ends an **Open…** that accepts `.sng`, `.txt`, `.pdf`.
A `.sng` skips `extract_payload` entirely — it *is* the payload. On a
hit: validate with the existing `model` migration path (the payload
records `format`, so a v0.16 file found inside a v0.21 PDF migrates
exactly as a `.json` would), then open it as a new unsaved song named
after the file. On a miss: say plainly that the file has no embedded
document and offer the free-text route (import the whole TXT into a
single `render:"free"` section), which is a genuinely useful fallback and
about six lines of code.

**Tests.** Round-trip a document with every item kind through TXT and
through PDF and assert the recovered dict equals the original;
payload-free files return `None`; a truncated payload raises cleanly
rather than half-importing. A `.sng` written by v0.16 still opens, which
the existing migration tests already cover.

## 2. Techniques — palm muting, slides, legato, bends

**The ask.** "Tab features implementation or documentation, such as palm
muting, slide, bending, legato, etc."

**The principle.** These are characters typed *in* the tab, not a mode,
a toolbar, or a per-note dialog. Every tab reader already knows them, and
every one of them is one character wide, which is what makes them
compatible with a fixed-width grid.

### 2.1 Vocabulary

| Typed | Means | Where |
|---|---|---|
| `5/7` | slide up | tab cell, lick position |
| `7\5` | slide down | tab cell, lick position |
| `5h7` | hammer-on | tab cell, lick position |
| `7p5` | pull-off | tab cell, lick position |
| `7b` | bend | tab cell, lick position |
| `7b9` | bend to pitch | tab cell, lick position |
| `7r` | release | tab cell, lick position |
| `5~` | vibrato | tab cell, lick position |
| `x` | muted / dead note | already supported |
| `PM` | palm mute, over the run that follows | its own row |

The first nine are *within* a position: the cell holds `5/7` where it
held `5`. This is why §1's fixed-width cell work matters — a lick's cell
width is already computed as the max token width across the whole lick,
so `5h7` simply widens every cell to three and the columns stay aligned.
Nothing in the layout needs to change.

Palm muting is different in kind: it spans positions rather than living
in one. It gets its own row above the tab, printed as `PM- - - -` over
the span it covers, in grey (reusing the span mechanism v0.21 added for
rests). In the chart-line grammar it's a mark: `pm` opens it, `pm/`
closes it, and an unclosed `pm` runs to the end of the line.

### 2.2 What it touches

- `grammar.py` — widen `_LICK_FRET_RE` from
  `^(?:[-x]|0|[1-9][0-9]?)$` to a technique-aware pattern. Keep the
  *validation* strict: `5/7` is legal, `5/` is not, `5h` is not, `7b9`
  is, `9b7` (bending down) is not. Add `pm` / `pm/` to `MARK_NAMES`.
- `transpose.py` — a technique token holds *two* frets. Transposition
  must move both and must apply the existing off-the-neck rule to the
  pair as a unit: if either end would fall off, leave the whole token
  alone. Getting this wrong turns `5/7` into `5/24` silently, so it is
  the test to write first.
- `render.py` — nothing, if the cell-width rule is respected. Add
  `ROLE_PM` for the palm-mute row.
- The tab grid in both front ends — nothing structural; the cell is a
  free-text entry that currently rejects these on parse.
- Documentation — a row per technique in the in-app notation reference
  and in `wiki/Chart-Line-Syntax.md`. The *documentation* half of the ask
  is not optional: a notation nobody can look up is a notation that gets
  used once and then misread a month later.

### 2.3 Scope discipline

No bend-amount notation (`7b½`, `7b1`), no tapping, no harmonics, no
tremolo picking in the first pass. Each is a real technique and each
costs a character that then can't mean anything else. Ship the nine
above, use them for a month, and add from what's actually missing.

## 3. Dynamics — accents and crescendo

**The ask.** "Add crescendo or accent feature on all, tab or chords."

Two different shapes, and they should not be forced into one syntax.

### 3.1 Accent — one item, marked

An accent belongs to the thing it's on, so it's a suffix, not a mark:
`5A!` accents that token, `{G 5! 7 5}` accents the first position of the
lick, `5!` in a tab cell accents that beat. Prints as `>` above the item
in the fret row (the row is already there and usually half-empty), or as
a bold symbol where there is no fret row.

`!` is free in the current grammar, is one character, and reads as
emphasis to anyone who has ever typed. Store it as `"accent": True` on
the item rather than as part of the symbol string, so transposition,
unparse and reference expansion don't have to know about it.

### 3.2 Crescendo — a span, opened and closed

A hairpin covers a run, so it's a pair of marks on the chart line:

```
cresc  5A  7D  8F  cresc/     dim  5A  7D  dim/
```

Add `cresc`, `cresc/`, `dim`, `dim/` to `MARK_NAMES` and to the
quick-insert palette. `render.mark_spans()` already resolves paired
marks into spans for the ending brackets, so the resolution logic exists;
what's new is the drawing.

**Printed form.** Under the symbol row, over the columns the span covers:

```
  5   7   8
  A   D   F
  <————————————
```

A real hairpin (two converging lines) is the right answer in the PDF,
where `hline()` can draw at an angle — about fifteen lines in
`_build_pdf`. In TXT it degrades to `<———` / `———>`, which is what a
monospace file can honestly do.

Static marks (`f`, `mf`, `p`, `pp`) are *not* worth a grammar entry: the
quoted annotation already handles them (`"f"`), and a hand-written stage
chart rarely carries more than one. Revisit only if that proves wrong in
use.

### 3.3 "on all, tab or chords"

The reading to implement: accents work in all three places (chart token,
lick position, tab cell) because they attach to an item and all three
have items. Hairpins work on the *chart line* only in the first pass —
a hairpin spanning a tab grid's measures is a different drawing problem
(it has to span measure columns and wrap with them) and should wait until
the chart-line version has been used and is known to be right.

## 4. Parts — several instruments in one section

**The ask.** "Add different instruments on same section (different part
so you can choose what to see/print)."

**What already exists.** Rather more than it looks. `instrument` is a
per-section field; `export.build_pdf(doc, instruments=...)` and
`build_song_lines(doc, instruments=...)` already filter sections by it;
`cli.py --instrument` already exposes that; `uniform_instrument()`
already decides whether to print the instrument in the header or per
section. So "one file, two instruments, print either" works *today*
provided each section belongs to one instrument.

What doesn't work is the actual ask: **the same section, two parts.**
Verse 1 has a bass line *and* a guitar part, and they are the same eight
bars of the same song, not two sections that happen to be adjacent.

### 4.1 Model

Add an optional `parts` list to a section. A section has either `items`
(today's shape, one instrument) or `parts`:

```python
{
  "id": "verse_1", "name": "Verse 1", "type": "Verse", "repeat": 4,
  "parts": [
    {"instrument": "Bass (4-string)", "items": [...], "render": "chart"},
    {"instrument": "Guitar (6-string)", "items": [...], "render": "tab"},
  ],
}
```

`render` moves onto the part, because a bass line is a chart and the
guitar figure under it may want to be a tab grid. `instrument` on the
section becomes the first part's instrument for compatibility.

**Migration is the whole risk of this item.** Every read path in
`songmap.py`, `render.py`, `export.py` and both front ends currently
reaches for `sec["items"]`. The way to do this without a rewrite is a
single accessor:

```python
# songmap.py
def parts_of(sec: dict) -> list[dict]:
    """A section's parts. A single-instrument section is one part —
    so every caller can stop caring which shape it is."""
    if sec.get("parts"):
        return sec["parts"]
    return [{"instrument": sec.get("instrument"), "items": sec.get("items", []),
             "render": sec.get("render", "chart")}]
```

then convert callers to loop over `parts_of(sec)` *before* anything can
write a multi-part section. A one-part loop is behaviour-identical, so
that conversion is a pure refactor with the existing 216 tests as its
proof. Only once it's green does the UI get the ability to add a second
part. `model.migrate()` leaves v2 files alone; `FORMAT_VERSION` goes to
3 only when a `parts` key is actually written.

### 4.2 Printing and the UI

- Export gains a part filter, not just a section filter: the existing
  `instruments=` argument starts selecting *parts*, so "print the bass
  chart" prints Verse 1's bass part and skips its guitar part.
- The section card grows a part strip — one row per part, each with its
  own instrument picker, render mode, chart line, and a show/hide eye.
  The eye is view-only state and belongs in the front end, *not* the
  document: it is about this session's screen, not about the song.
- The page estimate (`estimate_section_lines`) sums over visible parts.
  Expect a one-page song to become two when both parts print; the "Fit to
  one page" scale option already handles that honestly.

### 4.3 What not to do

Don't let parts have different repeat counts, different names, or their
own annotations. The moment two parts can disagree about structure they
are two sections, and the model has those already.

## 5. Lyrics under the chart

**The ask.** "See how it works design wise with the lyrics."

The v0.19 Lyrics panel deliberately stopped short: lyrics are stored
(whole-song and per-section), optionally printed as a block, and never
auto-fetched. Everything beyond that is a *layout* question, and it is
the hardest one in the program, because a one-page stage chart and a
lyric sheet want opposite things — the chart wants density, the lyrics
want line breaks where the singer breathes.

### 5.1 Three candidate layouts

**(a) Block under the section.** What ships today. The lyrics print as
their own paragraph beneath the chart row. Costs one line per lyric line;
a 12-section song with lyrics is three or four pages. Correct, unexciting,
and already works.

**(b) Two columns.** Chart on the left half, lyrics on the right half,
per section. Roughly halves the page count versus (a) and keeps the
chart's density intact. The section band spans both columns, so the
structure still reads down the page. **This is the one to build.** It is
a change to `_build_pdf`'s `BODY_X` / width maths and a matching wrap in
`build_song_lines`, and it needs no model change at all.

**(c) Aligned — a syllable under its chord.** The thing real chord
sheets do. It is also the reason chord sheets are not one page: aligning
syllables to positions forces the chart to the lyric's rhythm, and a
section that was one dense row becomes four sparse ones. It additionally
requires an alignment model (which syllable sits under which item) that
nothing in the current data model expresses, and that no importer could
infer. **Don't build this.** If the pull towards it persists, the honest
version is a separate "lyric sheet" export — a second document from the
same file — not a mode of the stage chart.

### 5.2 The decision to make on paper first

Print one real song three ways — (a), (b), and the handwritten original
— and see which one is usable on a stand. The handwritten sheets that
this whole program is a typed version of mostly *don't carry lyrics at
all*; they carry structure, and the singer knows the words. If that
holds up, the right answer to this item is (b) plus a per-section "print
lyrics" toggle that is off by default, which is nearly what exists now.

## 6. Suggested order

| Step | Item | Why here |
|---|---|---|
| 0 | §1.0 `.sng` import in the browser | Closes a gap the desktop app hasn't got; no new format work |
| 1 | §1.1 TXT payload + import | Smallest, highest value, no UI |
| 2 | §1.2 PDF attachment | Same machinery, contained |
| 3 | §2 techniques | Self-contained; transposition is the only sharp edge |
| 4 | §3.1 accents | One character, one flag on an item |
| 5 | §5.1(b) two-column lyrics | Layout only, no model change |
| 6 | §3.2 hairpins | Needs the PDF drawing work |
| 7 | §4.1 `parts_of()` refactor | Pure refactor, tests as proof |
| 8 | §4.2 multi-part UI | Only once 7 is green |

Steps 1–4 are each a session. Step 7 is the one to do on a quiet evening
with the full test suite in a watch loop.
